# 모델 서빙에서 라우팅, 스케줄링, 오토스케일링, 멀티 LoRA

질문 먼저 던져보고 시작하겠다

- 엔진 하나에 RadixAttention 적중률이 80%가 나왔는데 레플리카를 4개로 늘렸더니 20%로 떨어졌다. 왜 그럴까?
- gpu 사용률이 95퍼인데 오토스케일러가 스케일아웃을 하지 않는다 애초에 **gpu 사용률로 스케일하면 안되는 이유가 무엇일까?**
- 유료 고객의 대화형 요청과 무료 사용자의 배치 요청이 같은 큐에 섞이면 누가 먼저 처리되어야할까
- 고객사 300곳이 각자 파인튜닝한 모델을 달라고하면 gpu가 300세트가 필요한가?
- 트래픽이 갑자기 두 배가 됏을때 새 파드가 첫 토큰을 배틱까지 몇 초가 걸릴까

이 질문들은 전부 엔진 바깥에 정답들이 존재한다 엔진이 n개가 되는순간 생기는 문제들이기 때문이다

엔진 하나의 성능을 고민했을때는 배치를 얼마나 크게 만들고 kv를 얼마나 아끼는가 커널, 병렬화, pd 분리, 투기적 디코딩, 양자화 등에 대해서 고민했다면

이번에는 클러스터 성능 = 요청을 어디로 언제 몇 개의 엔진으로 보내는지를 고민하는 것이다.

```
[클라이언트]
     ↓
[게이트웨이 / 라우터]      ← 어디로 보낼까 (캐시 인지 라우팅)
     ↓                     ← 지금 받을까, 미룰까, 버릴까 (admission / flow control)
[엔진 레플리카 × N]        ← 엔진 안에서 누구 먼저 (스케줄링 정책)
     ↓                     ← 배칭, KV, 커널, 병렬화, PD 분리
[GPU]
     ↑
[오토스케일러]             ← N을 몇으로, 늘리는 데 얼마나 걸리나
                           ← 모델 하나로 고객 수백 명 (멀티 LoRA)
```

| 사례 | 상황 | 하드웨어 | 2편에서의 핵심 고민 |
|------|------|----------|-------------------|
| A. 사내 코딩 어시스턴트 | 엔지니어 200명 → 1,000명으로 확장 | 8×H200 1노드 → 4노드 | 출근 시간 피크, 레플리카 간 캐시 |
| B. 문서 QA / RAG | 같은 문서 반복 질의 | 4×H100 (8B 모델, DP 4) | 라우팅이 캐시 적중률을 결정 |
| C. 대형 MoE 대규모 서빙 | DeepSeek V4급 | 12노드 / 96 GPU, PD 분리 | 프리필·디코드 풀 각각 스케일링 |
| D. 멀티테넌트 SaaS (신규) | 고객사 300곳, 각자 LoRA | 4×H100 | 어댑터 관리, 테넌트 간 공정성 |

### 개요

레플리카를 여러 개 띄우는 이유는 용량이 모자라거나 하나가 죽으면 서비스가 죽거나 롤링 업데이트를 해야하는 경우등이 있다

문제는 레플리카 앞에 **평범한 L7 로드 벨런서 (라운드 로빈, least-connections)**를 두는 순간 생기게 되는데 웹 서버에서는 잘 통하던 이 방식이 llm에서는 세 가지 이유로 깨지게 된다

1. **요청의 비용은 균질하지 않다**: 웹 요청은 대부분 비슷한 비용이지만 llm 요청은 100토큰 질문과 32k 토큰 문서 요약이 같은 요청 1건이 된다 출력도 10토큰 짜리와 4,000 토큰 짜리가 섞인다 **커넥션 수는 이제 더이상 부하가 아닌것이다.**
2. **엔진이 상태를 가진다**: RadixAttention, 접두사 캐싱은 엔진이 이전 요청의 kv를 기억한다라는 데서 이득을 보는데 로드밸런서가 엔진을 **서로 교환 가능한 stateless서버**로 취급하면 이 상태가 무의미해진다.
3. **진짜 부하 신호는 HTTP 레벨에 없음**: 큐 깊이나 kv캐시 사용률, 현재 디코딩 중인 시퀀스 수는 엔진 내부 값이고 로드밸런서는 현재 이걸 모른다.

**직접 계산을 해보면 - 라우팅 방식에 따라 캐시가 달라지는 방식**

라운드로빈으로 예시를 들어보자, 레플리카 4개가 같은 문서를 각자 따로 캐시에 담았을때 gpu 4장의 메모리가 캐시로는 1장 분량밖에 되지 않을것이다, 같은 문서를 항상 같은 레플리카로 보내면 4장이 각자 다른 문서를 담으니 4장 분량을 온전히 쓰게되는 장점이 있다.

그러나 그렇지 않게되면 라운드로빈같이 그냥 순서대로 돌아가면서 보내게되면 캐시미스가 발생해, 연산을 다시하게 되는문제가 있다 이것이 라우팅의 중요성이다.

사례 B H100 4장에 8B 모델을 한장에 하나씩 DP=4로 올렸을때

일단 한대에 올리게 된다면,

```
[1] 토큰당 KV 크기 (Llama-3.1-8B)
    2 × 32층 × 8 KV헤드 × 128차원 × 2바이트(BF16)
    = 131,072 바이트 = 128 KiB / 토큰

[2] 레플리카 하나의 KV 캐시 용량
    80GB × 0.88(mem-fraction-static) ≈ 70GB
    - 가중치 16GB
    ≈ 54GB → 54GB ÷ 128KiB ≈ 41만 토큰

[3] 워크로드: 자주 질의되는 문서 200개 × 평균 8K 토큰
    = 160만 토큰 (이게 "캐시에 있었으면 하는" 워킹셋)
```

문서 200개를 전부 기억하려면 160만 토큰이 필요하고 레플리카 하나로는 1/4 정도로 나눠 담는다

**라운드 로빈으로 보내게 되면**

문서 A에 대한 첫번재는 레플리카1, 두번째는 레플리카2, 세번째는 레플리카3 이렇게 돌아가며 가게된다.

- 레플리카마다 문서 200개 160만 토큰을 기억하려하지만 약 41만 토큰뿐의 캐시가 존재
- 새문서가 들어올때마다 오래된 문서가 밀려남
- 질문이 들어왓을때 그문서가 마침 캐시에 남아있을 확률은 약 25퍼 (캐시히트)
- 나머지 75%는 문서 8k토큰을 처음부터 다시 프리필

그래서 라우터가 같은 문서를 같은 레플리카로 보내게된다면 캐시히트를 높일수있게된다.

| | 라운드로빈 | 같은 문서 → 같은 레플리카 |
|---|---|---|
| 레플리카 하나가 기억해야 할 문서 | 200개 (160만 토큰) | 50개 (40만 토큰) |
| 레플리카 하나의 캐시 자리 | 50개분 (41만 토큰) | 50개분 (41만 토큰) |
| 캐시 적중률 (대략) | 약 25% | 처음 한 번 빼고 거의 전부 |
| 클러스터 전체에 담긴 문서 | 4개가 비슷한 문서를 겹쳐 담음 (중복) | 겹침 없이 200개 전부 |

## 캐시 인지 라우팅 - 어디로 보낼까

### 캐시 친화 vs 부하 균형

캐시만 보면 답은 해당 접두사를 가진 레플리카로 보낸다만 하면 된다.

그런데 **인기 있는 접두사가 존재하면?** 예를들어 모든 요청이 같은 3k 토큰짜리 시스템 프롬프트로 시작하면, 캐시만 보는 라우터는 **모든 요청을 한 레플리카로 몰아넣는다** 나머지 3개는 놀고 하나는 큐가 폭발한다.

```
캐시만 보는 라우팅  → 적중률 ↑, 핫스팟 → TTFT p99 폭발 ❌
부하만 보는 라우팅  → 균등 분산, 캐시 무의미 → 프리필 반복 ❌
둘을 섞는다         → 적중률을 조금 양보하고 핫스팟을 피함 ✅
```

> 비유하면 단골이 많은 1호점으로 손님을 계속 보내면 1호점 앞줄이 50미터가 되고 어느순간부터 1호점은 메뉴를 아는 직원이 있어서 주문이 빠르다는 이득보다 줄 서는 시간이 더 길어지기에 그 손익분기점을 계산해야하고 그 역할은 라우터가 한다.

모든 캐시 인지 라우터는 결국 이 두 항을 어떻게 섞느냐에 따라 달라진다

**라우터가 캐시 상태를 아는 세 가지 방법**

| 방식 | 캐시 상태를 아는 방법 | 장점 | 약점 | 대표 구현 |
|------|---------------------|------|------|----------|
| **근사 (Approximate)** | 라우터가 "내가 어디로 뭘 보냈는지"를 자기 트리에 기록하고, 아직 캐시에 있다고 **가정** | 엔진 수정 불필요, 단순 | 엔진이 축출했는데 라우터는 모름 (드리프트) | SGLang Model Gateway `cache_aware`, llm-d 기본 스코어러, Dynamo `--no-kv-events` |
| **정밀 (Precise)** | 엔진이 KV 블록 저장/축출 **이벤트를 발행**하고 라우터가 전역 인덱스를 유지 | 실제 캐시 상태 반영 | 이벤트 버스 필요, 오버헤드 | Dynamo KV Router (기본), llm-d precise 스코어러 |
| **해시 (Hash)** | 접두사를 해시해서 일관 해싱 | 상태 없음, 매우 쌈 | 부하를 모름, 핫 접두사 대처 불가 | `prefix_hash`, `consistent_hashing` 정책 |
 
어느게 정답인지는 워크로드의 문제고 llm-d 문서에서는 기본 프로필이 요청 트래픽만 관찰해서 캐시 위치를 예측하는 근사 스코어러를 사용하고, vLLM 인스턴스의 실제 캐시 항목을 들여다보는 정밀 라우팅은 적중률을 더 높이며 향후 기본값이 될 예정이라고 설명한다. Red Hat 문서도 근사 방식은 GA이자 대부분의 배포에서 권장되고 정밀 방식은 접두사 패턴이 크게 변하는 워크로드에 맞다고 정리한다.

### **SGLang Model Gateway의 cache_aware 들여다보기**

먼저 이름 정리, 예전 이름은 SGLang Router(SGL Router)다.

2025년 12월에 이름이 바뀌어서 소스 디렉터가 `sgl-router/` 에서 `sgl-model-gateway/`로, prometheus 메트릭 접두사가 sgl_router_* 에서 smg_* 로변경되었다 대시보드 쿼리가 옛날 이름으로 짜두면 조용히 비어있으니 주의

정책은 여러가지로 random, round_robin, cache_aware, power_of_two, bucket 등의 로드밸런싱 전략을 제공한다.

핵심인 `cache_aware`의 동작은 이렇게 생겼다

```
요청이 들어온다
  │
  ├─ 부하가 불균형한가?  (가장 바쁜 워커와 가장 한가한 워커의 큐 차이가 임계값 초과)
  │     └─ YES → 캐시 무시, 가장 큐가 짧은 워커로  (핫스팟 방지가 우선)
  │
  └─ NO → 각 워커별 "라우터 쪽 radix tree"와 요청의 최장 접두사 일치율 계산
          │
          ├─ 최고 일치율 > cache_threshold (기본 0.5)
          │     └─ 그 워커로  (캐시 적중 노림)
          │
          └─ 아니면 → 트리가 가장 작은 워커로
                      (= 캐시 여유가 가장 많은 곳에 새 접두사를 심는다)
```

마지막 분기가 중요한데, **처음 보는 접두사를 어디에 심느냐**가 미래 적중률을 결정한다.

아무데나심으면 나중에 같은 접두사 요청이 몰릴대 그 레플리카가 이미 바쁠 수 있다.

`--cache-threshold`는 캐시 라우팅을 위한 최소 접두사 일치율로 기분 0.5고 `--balance-abs-threshold` 기본값은 32다.

그리고 하나 기억할 것은 이 라우터의 트리는 **토큰이 아니라 텍스트 기준**이다. cache-aware 정책은 라우터 쪽에서 순수하게 접두사를 보는 방식이고 토큰이 아니라 텍스트 위의 radix tree다 엔진 내부의 토큰 기반 radix tree와 경계가 미묘하게 다를 수 있다는 뜻이다.

```bash
# 워커 2개 + 캐시 인지 라우팅
python -m sglang_router.launch_router \
  --worker-urls http://worker1:8000 http://worker2:8000 \
  --policy cache_aware \
  --cache-threshold 0.5 \
  --balance-abs-threshold 32 \
  --max-concurrent-requests 512
```

### Dynamo KV Router - 비용 함수로 보기

NVIDIA Dynamo는 이 긴장을 **명시적인 비용 함수**로 표현한다.

공식이 단순해서 이해하기 쉽다.

비용 공식은 `cost = overlap_scoree_weight * prefill_blocks + decode_blocks` 이고, 라우터느 비용이 가장 낮은 워커를 고른다 router_temperature를 0이 아닌 값으로 두면 정규화한 비용 로짓에 소프트맥스 샘플링을 적용하고 선택해 무작위성도 넣는다.

- `prefill_blocs`: 이 워커로 보냇을때 **새로 계산해야하는 블록수** (전체 블록 - 캐시 적중 블록). 프리필 비용 즉 TTFT쪽 항
- `decode_blocks`: 이 워커에서 지금 디코딩중인 활성 kv 블록 수로 디코드 부하 즉 ITL 쪽 항
- `overlap_score_weight`: 두 항의 환율

가상의 숫자로 직접 계산해보자 요청 4,096토큰, 블록 16토큰이면 256블록

```
워커 1: 캐시 적중 200블록 → prefill 56블록,  활성 디코드 900블록 (바쁨)
워커 2: 캐시 적중   0블록 → prefill 256블록, 활성 디코드 300블록 (한가)

weight = 1.0
  W1 = 1.0 × 56  + 900 = 956
  W2 = 1.0 × 256 + 300 = 556   ← 선택 (캐시를 버리고 한가한 쪽)

weight = 3.0
  W1 = 3.0 × 56  + 900 = 1,068
  W2 = 3.0 × 256 + 300 = 1,068   ← 동점

weight = 4.0
  W1 = 4.0 × 56  + 900 = 1,124   ← 선택 (캐시를 위해 바쁜 쪽을 감수)
  W2 = 4.0 × 256 + 300 = 1,324
```

같은 요청, 같은 클러스터 상태인데 weight 하나로 결정이 바뀌는걸 볼 수 있따

서빙 튜닝에서 최적 설정이 없다는 사실이 라우팅 층에서도 볼 수 잇는것이다

튜닝 방향은 직관적인데 weight를 1.0 키우다 보면 프리필 비용 절감 (TTFT 개선)을, 1.0보다 낮추면 디코드 성능 ITL을 우선한다. 

긴 프롬프트, 짧은 생성 같은 프리필 위주 워크로드는 weight를 올리고 짧은 프롬프트, 긴 생성같은 디코드 위주 워크로드는 weight를 내린다.

최신 버전은 계층 캐시 (HBM -> CPU DRAM -> 디스크)까지 비용에 넣는다. gpu 위의 적중 블록, 호스트 메모리 적중, 디스크 적중에 각각 다른 가중치를 매겨 프리필 블록에서 차감하는 식이다. cpu dram에 있는 캐시는 HBM에 있는 캐시보다 가져오는데 비싸니까 (H100 HBM 약 3,350 GB/s vs PCIe 5.0 약 63 GB/s)를 덜 쳐주는 것이다 "다시 계싼할까 가져올까" 의 손익분기 라우터 비용 함수 안으로 들어온샘

### llm-d 와 Gateway API Inference Extension - K8s 표준

라우팅 로직을 엔진마다 따로 만드는 쿠버네티스 gateway api의 확자응로 표준화하려는 흐름이 있다.

이게 gateway api inference extension GAIE(게이아님)이고, llm-d가 그위에 올라간 스택이다

구조는 3단계 파이프라인에 있는데 red hat 블로그 설명으로는 EPP(Endpoint picker)가 요청ㅇ르 보내기 전에 모든 모델 서버 파드를 검사해 최적 대상을 찾고 기본 스코어러는 각 파드가 이 요청의 접두사를 얼마나 캐시하고 있는지를 본다 점수가 가장 높은 파드를 고르고 동점이면 무작위다

```
요청
 ↓
[Filter]  쓸 수 없는 파드 제거 (draining 중, 다른 모델, LoRA 미보유 등)
 ↓
[Score]   남은 파드마다 스코어러별 점수 × 가중치 합산
            - prefix-cache-scorer   (캐시 친화)
            - queue-scorer          (큐 길이)
            - kv-cache-utilization  (KV 여유)
 ↓
[Pick]    최고점 선택
```

기본 프로필은 prefix-cache-scorer, queue-scorer로 파드를 점수 매기고, prefix-cache 쪽 가중치를 높게 둔다. Dynamo의 비용 함수와 구조가 똑같다. 표현만 비용 최소화냐 점수 최대화냐의 차이이다.

흥미로운 개선 하나: **콜드 요청 분산** 처음 보는 접두사를 아무데나 심으면 나중에 핫스팟이 된다는 위의 문제를 llm-d v0.4가 직접 다뤘는데 새 접두사 캐시의 씨앗이 되는 콜드 요청을 지능적으로 분산해주는 캐시 형성 중 핫스팟을 막는 스코어러에 넣었고 v0.3에서 보이던 대기 큐 진동을 없애 P99 TTFT를 50퍼 줄였다

그리고 SGLang 사용자에게 중요한 소식. v0.8에서 SGLang이 정밀 접두사 캐시 라우팅 경로에 들어왔다. 이젠 vLLM 전용이던 prefix cache 스코어러가 이제 SGLang 백엔드에서도 동작해서 이 최적화 엔진이 무관해졌다 같은 릴리즈에서 llm-d-inference scheduler는 llm-d-router-endpoint-picker로 이름이 바뀌었다 검색할때 두 이름은 다 기억해두자.

### PD 분리에서 라우팅

PD 분리 구조에서는 라우팅 결정이 두 번 일어나는데, 프리필 풀에서 하나, 디코드 풀에서 하나. 그리고 두 결정의 기준이 다르다.

```bash
python -m sglang_router.launch_router \
  --pd-disaggregation \
  --prefill http://prefill1:30001 9001 \
  --prefill http://prefill2:30002 \
  --decode  http://decode1:30011 \
  --decode  http://decode2:30012 \
  --prefill-policy cache_aware \
  --decode-policy power_of_two
```

- **프리피 풀:** 하는일이 접두사 kv캐시 계산이기에 캐시 적중 = 계산 생략이다. 그래서 cache_aware로 설정해뒀다.
- **디코드 풀:** kv는 프리필에서 **전송받는다** 디코드 노드의 접두사 캐시는 의미가 적구 관건은 메모리 여유 와 배치 크기다. 그래서 무작위로 두개 뽑아 덜 바쁜쪽을 고르는 power of two가 싸고 충분하다

> power-of-two-choices는 오래된 로드밸런싱 결과로 무작위로 하나 고르는것보다 무작위로 둘 뽑아 덜 바쁜쪽으로 고르는것만으로 최대 부하가 극적으로 줄어든다 전체를 다보는 비용없이 거의 최적에 가까워진다.

### Trade Off

- **핫 접두사 핫스팟**: 친화 라우팅의 영원한 숙제로 부하 임계값을 너무 느슨하게 잡으면 p99가 튀게된다.
- **근사 방식의 드리프트**: 라우터는 캐시가 있다고 믿지만 엔진은 이미 축출했다면 엔진 메모리 압박이 클수록 근사 라우터의 판단이 틀릴수잇다.
- **정밀 방식의 비용:** kv event bus(NATS, ZMQ등)라는 새 인프라와 새 장애 지점이 생긴다
- **라우터 레플리카간 불일치**: 라우터도 가용성을 위해 여러 개 띄우는데 각자 다른 트리를 들고 있으면 같은 접두사들을 서로 다른 워커러 보낸다. Dynamo는 라우터간에 요청 할당을 공유해서 이를 줄인다.
- **텍스트 vs 토큰 불일치:** 라우터가 텍스트 기준으로 일치를 계산하고 엔진이 토큰 기준으로 캐시하면 경계가 어긋날 수 있다.

#### Exmaple - 사례 B 적용

```
상황: 4×H100, 8B, DP=4. 문서 200개 반복 질의. 라운드로빈으로 운영 중.
증상: 레플리카별 sglang cache_hit_rate가 25~30%. 엔진 하나로 테스트할 땐 80%였다.

진단: 맨 앞의 라운드로빈 계산 그대로. 워킹셋 160만 토큰 vs 레플리카당 41만 토큰.
      라운드로빈이 워킹셋을 4벌 복제 중.

조치:
  1. Model Gateway를 cache_aware로 앞단에 둔다
  2. 프롬프트 구조 확인: [시스템 프롬프트][문서][질문] 순서인지 (변하는 값은 뒤로 보내야 접두사가 공유된다)
  3. 문서 하나에 질문이 몰리는 인기 문서가 있는지 확인 → 있으면 balance 임계값을 보수적으로

기대: 레플리카당 워킹셋이 40만 토큰으로 줄어 용량 안에 들어옴 → 적중률 회복
검증: 레플리카별 적중률 + 레플리카별 큐 길이를 같이 본다. 적중률만 오르고 큐가 한쪽에 몰리면 핫스팟.
```

## Admission과 Flow Control - 받을까 미룰까 버릴까

라우터가 어디로를 정한다면 그 앞에 지금 받아도 될까를 정하는 층이 필요하게 된다

큐에 넣어두면 언젠가는 처리된다? 용량을 넘는 트래픽이 들어오면 대부분의 시스템은 일단 큐에 쌓고 언젠간 처리되겠지 한다.

그런데 이게 왜 위험한지 숫자로 먼저 경험을 해보자

가장 단순한 대기열 모델 M/M/1 에서 큐 대기시간은 이렇다

```
평균 대기 시간 = ρ / (1 - ρ) × 평균 서비스 시간
ρ = 사용률 (도착률 / 처리율)
```

| 사용률 ρ | 대기 시간 (서비스 시간의 몇 배) |
|---------:|------------------------------:|
| 50% | 1배 |
| 70% | 2.3배 |
| 80% | 4배 |
| 90% | 9배 |
| 95% | 19배 |
| 99% | 99배 |

연속 배칭 엔진은 M / M / 1이 아니지만 배치가 커질수록 처리율 자체는 오르니까 곡선의 모양은 그대로다

사용률이 어느 지점에 넘게되면 대기시간이 선형이 아니라 폭발적으로 늘어나게된다

엔진 최적화의 목표는 gpu를 꽉 채우는 것이었는데 그런데 **클러스터 전체를 95퍼센트로 돌리려는 순간 이 곡선의 무릎 위에 올라탄다** 트래픽이 5퍼만 튀어도 TTFT가 두배가 된다

### 해법: 일부러 빨리 거절하는게 전부를 느리게하는것보다 낫다

gootput을 다시 떠올려보자 SLO를 지킨 요청만 세는 처리량이다.

```
[방치]   100건 전부 받음 → 큐 폭발 → 100건 전부 TTFT 8초 → goodput 0
[차단]   100건 중 10건 즉시 429 → 90건은 TTFT 0.5초    → goodput 90
```

10건을 버려서 90건을 살렸다. 거절당한 10건도 빨리 거절당했으니 클라이언트가 재시도하거나 다른 리전으로 갈 수 있다. 8초 기다리다 타임아웃 되는것 보다 낫다

> 응급실 트리아지와 같다. 모든 환자를 도착 순서대로 받으면 심정지 환자가 감기 환자 뒤에서 죽는다. 포화 상태는 누구를 먼저, 그리고 누구를 다른 병원으로를 정해야한다.

### 우선순위 등급 InferenceObjective

GAIE에서는 이걸 표현하는 리소스가 `InferenceObjective`다. 

요청이 얼마나 중요한지를 선언한다.

게이트웨이의 AuthPolicy가 이 인증정보를 바탕으로 헤더 두개를 자동 주입하는데 같은 인증 출처의 요청을 묶어 공정 큐잉하는 `x-gateway-inference-fairness-id`와 InferenceObjective 리소스를 매칭해 우선순위 `x-gateway-inference-objective`이다.

```yaml
# 개념 예시 - apiVersion과 필드는 GAIE 버전마다 확인할 것
apiVersion: inference.networking.x-k8s.io/v1alpha2
kind: InferenceObjective
metadata:
  name: ide-autocomplete       # 사례 A: IDE 자동완성 - 사용자가 타이핑하며 기다림
spec:
  priority: 100
  poolRef:
    name: coder-pool
---
apiVersion: inference.networking.x-k8s.io/v1alpha2
kind: InferenceObjective
metadata:
  name: chat-standard          # 일반 대화
spec:
  priority: 0
  poolRef:
    name: coder-pool
---
apiVersion: inference.networking.x-k8s.io/v1alpha2
kind: InferenceObjective
metadata:
  name: nightly-code-review    # 야간 배치 리뷰 - 늦어도, 버려도 재시도 가능
spec:
  priority: -10
  poolRef:
    name: coder-pool
```

포화를 판단하는 주체는 Saturation Detector다. 핵심은 이게 HTTP 커넥션 수가 아니라 kv와 큐를 본다는 점이다.

EPP의 Flow Control 층은 http connection 수가 아니라 kv 캐시와 큐 포화 지표같은 물리적 용량을 다스리도록 설계됐다.

음수 우선순위의 처리는 모드에 따라 다르다. 기존 admission 모드에서는 포화시 바로 거절되지만 flow control이 켜져있으면, 음수 우선순위 요청도 즉시 거절되지 않고 자기 전용 큐에 보관됐다가 디스패치되거나 만료될때까지 기다린다. 그래도 한계를 넘으면 낮은 우선순위 요청을 428 or 503으로 아예 떨어뜨리고 일반 우선순위 요청은 계속 큐에 넣는다.

### 재시도 막기

429를 던졌는데 클라이언트 1,000개가 즉시 동시에 재시도하면 포화가 더 심해진다 이걸 retry strom이라고 부른다.

- 서버 `Retry-After` 헤더로 언제 다시 오라고 알려준다
- 클라이언트: 지수 백오프 + Jitter(무작위 지연) 로 재시도 시점을 흔부린다
- 게이트웨이: 서킷 브레이커로 망가진 워커를 잠시 빼둔다

SGLang Model Gateway도 이 층을 갖고있다. 지터를 넣은 재시도, 워커 단위 서킷 브레이커, 큐잉을 동반한 토큰 버킷 rate limiting, 백그라운드 헬스체크를 제공한다

### Trade Off

- **우선순위는 용량을 예약하지 않는다**: Dynamo 문서에서 우선순위는 쿠머네티스의 PriorityClass or GPU 선점이나 강제 admission 정책이 아니며 높은 우선순위 요청을 위한 용량을 예약하지 않는다 높은 등급이 항상 빠르려면 등급별로 풀을 나누거나 용량을 따로 잡아야한다.
- **포화 임계값 튜닝이 어렵다**: 너무 낮으면 멀쩡한 요청을 버리고, 너무 높으면 이미 무릎을 넘어 장애가 난 뒤에야 반응하기 때문에 임계값 근처에서 상태가 뒤집히는 진동도 생긴다
- **단일 워크로드엔 과잉**: sla 요구가 균일한 단일 워크로드 유형만 있다면 flow control은 불필요한 복잡도만 더한다.

## 엔진 내부 스케줄링 정책 - 누가 먼저

라우터가 요청을 엔진에 넣었다. 이제 엔진의 대기큐안에서 **어떤 요청을 다음 배치에 넣을지**가 남게 된다.

연속 배칭은 자리가 나면 즉시 넣는다까지만 정하고 누구를 넣을지는 별개의 문제다.

기본값은 대부분 FCFS(선착순)이다. 단순하고 예측 가능하지만 아래 세가지문제가 존재한다.

1. **캐시를 모름**: 캐시에 접두사가 잇는 요청이 뒤에 있어도 앞의 미스 요청부터 처리한다.
2. **길이를 모른다**: 짧은 요청이 긴 요청 뒤에서 기다릴 수 있다 (head of line blocking)
3. **사람을 모름**: 한 사용자가 요청 1000개를 밀어넣으면 다른 사용자는 전부 뒤에서 대기하게된다.

각각에 대한 해법을 보자

### 캐시 인지 정책 - LPM과 DFS-weight

SGLang은 정책을 여러개 가지고있다. 캐시 인지 정책으로 캐시된 접두사가 긴 요청을 우선시하는 LPM(Longest Prefix Match)과 깊이 우선 가중으로 캐시 재사용을 개선하는 DFS-Weight가 있고, 캐시 무관 정책으로 FCFS가 가장 긴 출력 먼저하는 LOF, 무작위 등이 있다

**LPM이 왜 적중률을 올릴까?** 캐시는 시간이 지나면 축출이 된다. 지금 캐시에 접두사가 있는 요청을 먼저 처리하면 그 접두사가 축출되기전에 써먹는다. 뒤로 미루면 그 사이에 다른 요청이 들어와 LRU로 물러날 수 있다.

**DFS-weight는** Radis Tree를 깊이 우선으로 순회하는 순서로 요청을 처리한다. 같은 서브트리 (공통 접두사)를 가진 요청들을 **연달아 처리**해서 그 서브트리가 캐시에 있는 동안 몰아서 쓰는것이다

여기서 중요한 실측 교훈 하나. H100 에서 공유 접두사 워크로드 FCFS, LPM을 비교했더니 LPM과 FCFS가 통계적으로 같았고 2% 미만 차이쯤으로. LPM의 이득은 캐시 압박이 있어야 나타나며 gpu메모리가 넉넉하면 무작위가 아닌 어떤 정책이든 똑같이 좋다는 결론이 있다. -> 오버엔지니어링ㄴㄴ하라고

**캐시가 모든걸 담을 수 있으면 순서는 상관 없다** 축출이 일어나야 순서가 의미를 갖는다. 그래서 정책 비교 벤치마크를 할 때는 `--mem-fraction-static`을 낮춰서 일부러 캐시 압박을 만들어야 차이가 보인다.

TradeOff: LPM은 캐시 적중을 늘리도록 요청을 재정렬하지만 스케줄링 오버헤드가 더 든다. 그리고 캐시에 없는 요청은 계속 뒤로 밀려서 기아 상태가 될수도 있다.

### 길이 인지 - SJF 근사와 출력 길이 예측 

대기 시간 평균을 최소화하는 고전적 해법은 **SJF(Shortest Job First)**, 짧은 작업부터 처리하는거다.

문제는 LLM에서 작업 길이 (출력 토큰 수)를 미리 모른다는것이다 입력 길이는 알지만 출력은 EOS가 나와야 끝나니까..

그래서 연구들은 출력 길이를 예측한다. 정확한 값을 맞히기는 어렵지만 순서만 맞히면 된다는 관찰이 핵심인데 "Efficient LLM Scheduling by Learning to Rank"는 요청 배치 안에서 출력 길이를 상대적 순위를 learning to rank로 예측할 수 있음을 보이고 이를 써서 기존 방식보다 SJF에 더 가깝게 근사하는 스케줄러를 만들었다

```
FCFS:   [긴 요청 4000토큰] [짧은 요청 50] [짧은 요청 30] [짧은 요청 80]
        → 짧은 요청 셋 다 긴 요청이 끝날 때까지 대기 (배치 슬롯이 꽉 찼다면)

SJF 근사: [짧은 30] [짧은 50] [짧은 80] [긴 4000]
        → 평균 대기 시간 크게 감소, 긴 요청은 조금 더 늦게 끝남
```

TardeOff: 이번에는 긴 요청이 기아가 될수있다 실제 구현은 그래서 기다린 시간만큼 우선순위를 올려주는 aging 을 같이 쓴다

반대 방향도 있다. 배치(오프라인) 작업은 평균 대기시간보다 처리시간이 중요하니까 긴 것부터 넣는 LOF가 유리할수있다 긴 작업을 먼저 깔아두고 짧은것들로 빈자리를 메우는 식이다

### 사람 인지 - 공정성과 VTC

멀티테넌트 (사례D)에서 가장 현실적인 문제인데 고객사 하나가 배치 작업으로 요청 1만개를 밀어넣으면 FCFS는 나머지 299개 고객사가 전부 그 뒤에 선사

흔한 대응은 **RPM제한**인데, 그런데 이건 두 가지 이슈가 있다

1. 요청 수 자체는 비용이 아니다
2. 남는 용량이 있어도 제한에 걸린 고객은 못쓴다 -> gpu가 놀면서 고객 거절

OSDI '24의 "Fairness in Serving Large Language Models"가 이문제를 정면으로 다뤘는데 입력 출력 토큰 처리량을 반영하는 비용함수로 LLM 서빙의 공정성을 정의하고 연속 배칭 위에서 동작하는 공정 스케줄러 VTC(Virtual Token Counter)를 제안했다

아이디어는 네트워크 공정 큐잉에서 왔다 (fair queuing) 테넌트마다 카운터를 두고 토큰을 소비할 수록 증가하며 스케줄러는 카운터가 가장 작은 테넌트의 요청을 다음으로 고른다

```py
# VTC 개념 의사코드
counter = defaultdict(float)     # 클라이언트별 "지금까지 받은 서비스량"

def on_arrival(req):
    c = req.client
    if not has_queued(c):        # 새로 오거나, 한동안 안 오다 복귀한 클라이언트
        # 안 쓰는 동안 크레딧을 저축했다가 한꺼번에 쓰는 걸 막는다
        active = [counter[k] for k in backlogged_clients()]
        if active:
            counter[c] = max(counter[c], min(active))
    enqueue(req)

def pick_next():
    c = argmin(counter[k] for k in backlogged_clients())   # 가장 덜 받은 사람
    req = dequeue(c)
    counter[c] += W_IN * req.input_tokens                  # 프리필 비용
    return req

def on_decode_step(running_reqs):
    for r in running_reqs:
        counter[r.client] += W_OUT * 1                     # 출력 토큰 하나씩
```

- **token 단위:** 요청 단위가 아니라 토큰 단위로 세는것이 요청 크기 차이로 인해 생기는 불공정을 없앤다
- **입력과 출력의 가중치를 다르게줄 수 있다**: 디코드 토큰은 프리필 토큰보다 비싸니까 디코드는 메모리 바운드라서 조절 해서 공정하게 맞춘다
- **work-conserving**: 다른사람이 안쓰면 한 사람이 다 쓸수잇다 rpm 제한처럼 gpu를 놀게하지 않는다.
- **복귀시 카운터 올리기**: 위 코드에 `max(counter[c], min(active))` 이게 없으면 한 시간 안쓰다가 돌아온 고객이 그동안 쌓인 덜 받은 양으로 한동안 독점하게 된다 그래서 이렇게 막아주는것

보장도 있다. 논문은 VTC의 공정성 보장에 대한 엄밀한 증명을 제시하며 최적 경계의 2배 이내임을 보엿다 둘 다 대기중인 클라이언트 사이의 서비스 차이가 상수로 묶인다는 뜻이다.

### 우선순위와 선점

명시적 우선순위도 엔진에서 지원하는데 vLLM은 `--scheduling-policy priority`, SGLang은 `--enable-priority-scheduling`으로 시작하고 메모리 압박시 어떤 캐시 블록을 먼저남길지는 SGLang의 `--radix-eviction-policy priority` 같은 캐시 우선순위설정으로 정한다

우선순위가 진짜 효과를 내는 순간은 preemption(선점)이다 높은 우선순위 요청이 왔는데 kv메모리가 꽉 찼으면 실행중인 낮은 우선순위 요청을 물러나게 해야한다 여기서 재계산 vs 스윕 손익분기가 다시 등장한다. 물러난요청은 나중에 kv를 다시 계산하거나 cpu에서 가져와야한다.

### schedule-conservativeness 미래를 얼마나 비관적으로 볼지

SGLang의 이 파라미터는 이름이 너무 모호해서 많이들 지나치는데 스케줄러의 근본 문제를 담고있다

새 요청을 배치에 넣을 때 스케줄러는 이미 실행중인 요청들이 앞으로 몇 토큰들을 몇개 더만들지 추정해야한다

그만큼 kv메모리를 남겨둬야하니까 그런데 요청마다 `max_new_tokens=4096`을 걸어두고 실제로는 200토큰에서 EOS가 나오는 일이 흔하다.

```
너무 낙관적 (최대치보다 훨씬 적게 쓸 거라 가정)
  → 새 요청을 많이 넣음 → 실행 중 요청들이 생각보다 길어짐
  → KV 부족 → 실행 중 요청을 강제로 퇴출(retract) → 재계산 낭비

너무 비관적 (max_new_tokens를 다 쓸 거라 가정)
  → 새 요청을 적게 넣음 → 메모리가 남는데 배치가 작음 → 처리량 손해
```

SGLang 튜닝 가이드의 진단법이 실용적인데 요청이 큰 max_new_tokens를 걸지만, EOS, stop 문자열로 일찍 끝나는 경우가 흔하면 `--schedule-conservativeness`를 0.3 정도로 낮추고 토큰 사용률이 매우 높고 "KV cache pool is full. Retract requests" 경고가 자주 나오면 1.3 정도로 올린다. 분당 1회정도 간헐적 retract는 괜찮다.

#### 정책 선택 가이드 

| 상황 | 정책 | 이유 |
|------|------|------|
| 공유 접두사 많고 캐시 압박 있음 (사례 B) | LPM 또는 DFS-weight | 축출 전에 몰아서 쓴다 |
| 공유 접두사 많지만 메모리 넉넉 | FCFS로 충분 | 순서가 무의미 (위 실측) |
| 짧은/긴 요청 혼재, 대화형 | SJF 근사 + 에이징 | 평균 대기 시간 |
| 오프라인 배치 | LOF | 총 처리 시간 |
| 멀티테넌트 (사례 D) | VTC류 공정 스케줄링 | 한 테넌트 독점 방지 |
| SLA 등급 존재 | priority + (필요 시) 풀 분리 | 우선순위는 용량 예약이 아님 |

## 오토스케일링

### 왜 gpu 사용률로 스케일링 하면 안 될까?

웹 서비스에서 hpa를 cpu 70퍼에서 스케일아웃 등 같은 습관들을 gpu에서도 그대로 반영하면 안된다

1. 이유1: **nvidia-smi gpu사용률은 바쁜 정도가 아니라** 이 값은 샘플링 구간 동안 커널이 하나라도 돌고있던 시간의 비율이다. sm이 몇 개 일하고 있는지 메모리 대역폭을 얼마나 쓰는지와는 별개다. 디코드처럼 메모리 바운드 커널이 쉬지 않고 돌기만 하면 100퍼센트가 찍힌다.
2. 이유2: continous batching은 항상 바쁘게 만드는 특성이 있는데 llm-d에서 짚은걸 보면 cpu/gpu 사용률같은 전통적 지표는 포화가 이미 일어난 뒤에 반영하는 후행 지표이고 LLM 추론에서는 활성 배칭중 실제 부하와 무관하게 gpu사용률이 100퍼 근처에 고정되는 경우가 많아서 신호로서 믿기 힘들다

```
요청 10개 처리 중   → GPU 사용률 98%
요청 200개 처리 중  → GPU 사용률 99%
요청 200개 + 대기 300개 → GPU 사용률 99%   ← 이미 SLO 붕괴
```

그래서 아래와 같은 신호들을 대신 보는것이 좋다

| 신호 | 의미 | 장점 | 함정 |
|------|------|------|------|
| 큐 깊이 (대기 요청 수) | 처리 못 하고 쌓인 수요 | 포화의 직접 증거, 선행성 있음 | 0이 "한가함"이 아닐 수 있음 (아래) |
| 실행 중 요청 수 | 현재 동시성 | Little's Law와 직결 | 엔진 최대치 근처에서 평평해짐 |
| KV 캐시 사용률 | 메모리 압박 | 배치 크기를 막는 진짜 자원 | 접두사 캐시가 쌓이면 높게 보임 (축출 가능한 캐시 포함 여부 확인) |
| TTFT / ITL p95 | 사용자 체감 | SLO와 바로 연결 | 후행 지표, 노이즈 큼 |
| GPU 사용률 | 커널 실행 시간 비율 | 쉬움 | 위 설명대로 거의 쓸모 없음 |


llm-d가 권장하는 방향도 같다. 효과적인 LLM 오토 스케일링은 큐 깊이나 처리중 요청수, kv캐시 압박처럼 추론 시스템의 실제 상태를 반영하는 선제적이고 SLO 인지적인 신호가 필요하다

### 함정: 스트리밍 디코드 중에 0으로 줄어드는 레플리카

큐 깊이와 RPS가 둘 다 0인데 레플리카가 열심히 일하고 있는 상황이라고 보자. 긴 출력을 스트리밍 중인 요청들이다.

25분전에 긴 컨텍스트 요청을 하나 받아 8000토큰중에 4812번째 토큰을 만들고 있는 파드는 요청률도 0이고 큐 깊이도 0이다. HPA는 이 메트릭을 긁어가서 수요가 없다보고 축소 시계를 돌려버리면? 이런실수들을 피해야한다.

#### 대책

- 스케일 다운 판단에 실행중 요청수를 반드시 포함한다
- 파드 종료시 새 요청은 막고 진행중인 요청은 끝내는 drain 로직을 넣는다.
- `terminationGracePeriodSeconds`를 최대 생성 시간보다 길게 (기본 30초로는 긴 생성이 잘림)

### 스케일 업은 빠르게, 스케일 다운은 느리게

LLM 레플리카는 띄우는데 수 분이 걸리고 (콜드 스타트), 내리면 캐시가 날아간다 그래서 비대칭으로 튜닝한다

```yaml
# HPA behavior - 업은 공격적으로, 다운은 천천히
behavior:
  scaleUp:
    stabilizationWindowSeconds: 0        # 신호 오면 즉시
    policies:
    - type: Pods
      value: 2                           # 한 번에 2개씩
      periodSeconds: 60
  scaleDown:
    stabilizationWindowSeconds: 600      # 10분간 계속 한가해야 줄임
    policies:
    - type: Pods
      value: 1
      periodSeconds: 300                 # 5분에 하나씩만
```

KEDA로 엔진 메트릭에 직접 거는 예시

### PD 분리에서의 스케일링 - 다이얼이 두개

PD 분리를 하게 되면 프리필 풀과 디코드 풀이 따로 놀아야한다.

"입력이 긴 워크로드면 프리필 비중을 늘린다"는 그 비율을 조절을 자동화하는것이다.

Dynamo의 Planner같은게 이런 역할을 한다 프리필 디코드 워커 수를 조정하고 ARIMA, Prophet 등으로 미래 부하를 예측한다

계산 구졸르 보면 프리필, 디코드의 성격 차이가 그대로 녹아있다.

```
[프리필 레플리카 수]
  예측 부하 = 다음 구간 요청 수 × 다음 구간 평균 입력 길이 / 구간 길이
  프리필 레플리카 = ceil(예측 부하 / 프로파일링한 GPU당 프리필 처리량 / 엔진당 GPU 수)
  → TTFT는 프리필이 결정 (TTFT = 큐 대기 + 프리필)

[디코드 레플리카 수]
  ITL 목표를 만족하는 GPU당 디코드 처리량을 프로파일 데이터에서 보간
  → ITL은 디코드 배치 크기가 결정 (배치↑ → 처리량↑, ITL↑)

[보정 계수]
  prefill_correction = 실측 TTFT / 예상 TTFT
  decode_correction  = 실측 ITL  / 예상 ITL
```

보정계수가 필요한 이유는 무엇일까?

플래너가 레플리카수를 정할때 쓰는 숫자 (gpu하나가 초당 프리필 몇 토큰을 처리하나)는 미리 프로파일링 한 값이다.

그런데 프로파일링 환경과 실제 운영 환경이 다르다. 그 차이를 그대로 두면 레플리카 수가 계속 틀리게 된다.

가장 큰 차이는 접두사캐시로 프로파일링은 보통 캐시 없이 재는데 실제 운영에서는 캐시가 적중한 만큼 프리필을 건너뛴다. 숫자로보자 (가상의 값)

```
프로파일 값: 프리필 GPU 하나 = 초당 10,000 토큰 (캐시 없이 측정)
들어오는 입력: 초당 50,000 토큰

[보정 없이]
  플래너 계산: 50,000 ÷ 10,000 = 프리필 레플리카 5개
  실제: 캐시 적중률 60% → 진짜 계산할 토큰은 초당 20,000
       → 2개면 충분한데 5개를 띄움 → GPU 3개가 놂

[보정 있이]
  실측 TTFT가 예상의 약 0.4배로 나옴 → prefill_correction ≈ 0.4
  플래너가 예상 부하에 0.4를 반영: 50,000 × 0.4 = 20,000
  → 20,000 ÷ 10,000 = 프리필 레플리카 2개
```

반대방향도 있다 실제 입력이 프로파일때보다 길거나다른 요청과 섞여 서로 방해하면 실측 ttft가 예상보다 나쁘게 나온다. 그러면 보정 계수가 1보다 커지게 되고 플래너는 레플리카를 더 띄우게 된다 보정이 없으면 충분하다고 믿으니 SLO가 깨질수있는 상황을 방지할 수 있는 것이다

정리하면 보정계수는 **프로파일한 값과 현실과 얼마나 어긋났는가**를 실측으로 재서 레플리카 계산에 반영하는 장치다

이게 없으면 플래너는 캐시가 잘 맞을때 gpu를 낭비하고 환경이 나빠지면 용량이 모자라는데도 모른다.


### 이기종 하드웨어 - 싼 gpu부터 채우기

같은 모델을 H100, A100에도 L4에도 띄울수있다면 무작정 모든 풀을 같이 늘리는건 시간낭비다 llm-d WVA(Workload Variant Autoscaler)가 이 문제를 다루는데 모든 변형을 똑같이 늘리는 대신 가장 싼 변형에 우선 용량을 더하고 가잔 비싼변형에 먼저 빼서 지연 slo를 어기지 않으면서 최적화를 한다.

### 헤드룸 계산 - 오토스케일러가 따라잡을 수 있나

오토스케일러는 반응형이다 수요가 오른걸 보고나서 레플리카를 띄운다.

그 사이에 들어오는 수요는 기존 레플리카가 감당해야한다 이걸 계산해보자

엔지니어 1,000명에게 서빙한다고 쳤을때 오전 9시 출근이 피크타임이다.

```
[1] 트래픽 램프
    08:50 → 09:05 (15분 동안) 0.5 req/s → 10 req/s
    증가 속도 ≈ 9.5 / 15 ≈ 0.63 req/s per 분

[2] 새 용량이 서비스에 들어오기까지 (콜드 스타트 절에서 분해)
    감지:  메트릭 수집 15초 + HPA 주기 15초 + 판단 ≈ 1분
    콜드 스타트: 노드 3분 + 이미지 1분 + 가중치 1분 + 초기화 1분 ≈ 6분
    합계 ≈ 7분

[3] 그 7분 동안 늘어나는 수요
    0.63 × 7 ≈ 4.4 req/s

[4] 레플리카 하나가 SLO 안에서 감당하는 양 (가정, 벤치마크로 측정할 값)
    ≈ 3 req/s
    → 피크 진입 시점에 이미 약 2개 레플리카분의 여유가 떠 있어야 한다
```

- **예측 가능한 피크는 반응형으로 따라잡을 수 없다** 출근시간처럼 매일 오는 피크는 cron으로 미리 늘려두자 (KEDA cron 트리거)
- **콜드 스타트 시간이 헤드룸을 결정한다**. 콜드 스타트를 7분에서 2분으로 줄이면 필요한 여유 레플리카가 1/3 이하로 줄어드는데 아래에서 자세히 풀어보겠다.

## 콜드 스타트 - 새 파드가 첫 토큰을 뱉기까지


"파드가 뜨는데 오래걸린다"는 하나의 문제처럼 보이지만 실제로는 다섯단계로 이루어져있다

```
[1] 노드 프로비저닝      클라우드에서 GPU 노드 확보        수십 초 ~ 수 분 (재고 없으면 실패)
[2] 컨테이너 이미지 풀    vLLM/SGLang 이미지는 수~십수 GB   수십 초 ~ 수 분
[3] 가중치 로드          스토리지 → (CPU) → GPU           모델 크기 / 실효 대역폭
[4] 엔진 초기화          torch.compile, CUDA 그래프 캡처,  수십 초
                        커널 오토튜닝, KV 풀 할당
[5] 워밍업 & 헬스 체크    첫 요청은 비정상적으로 느림        수 초
```
> 위 범위는 자릿수 감각용이고 자기 환경에 단계별로 맞게 재야한다. 로그 타임스탬프만 잘 찍어도 어디가 병목인지 바로 보일것이다

### 가중치 로드

70B BF16 = 140GB

```
일반 클라우드 블록 스토리지 (~1 GB/s)   → 140초 ≈ 2분 20초
로컬 NVMe (~7 GB/s)                 → 20초
100Gbps 네트워크 (이론 12.5 GB/s)      → 11초
```

그런데 실제로는 이론값이 안나오고 기본 로더는 파일을 순차로 읽고 로컬 디스크에 한번 내려받은 다음 다시 읽고 페이지 캐시를 거치며 복사를 여러번하니까 대역폭을 100퍼 다 쓰지못해 더 느리게 나온다

### 가중치 로딩 가속 - Run:ai Model Streamer

해법의 핵심은 **병렬로 읽어서 로컬 디스크를 건너뛰고 바로 gpu로 보내는 것이다.**

Run:ai Model Streamer가 대표적인데 NVIDIA 설명으로는 스토리지에서 모델 가중치를 동시에 읽어 gpu 메모리로 바로 스트리밍하는 오픈소스 py sdk이다.

- Azure, 8 x H100 VM에서 Llama-3.1-8B(약 15GiB): Run:ai Streamer 3.61초 vs 기본 vLLM로더 15.48초로 약 4.3배 개선
- TPU에서 Qwen3-Coder-480B FP8: 스트리머는 280초미만에 로딩을 끝냈고 외부 스토리지 캐시하는 기본 로더는 630초 이상이 걸렸다. 메모리 효과도 큰데 기본 로더는 호스트 메모리를 모델 크기의 두배넘게 요구하지만 스트리머는 로컬 파일 캐시를 없애 피크 메모리를 모델 크기와 40gb 버퍼 수준으로 묶는다.

```bash
# vLLM - S3/GCS/Azure에서 바로 스트리밍
vllm serve s3://my-bucket/models/llama-3.1-70b \
  --load-format runai_streamer \
  --tensor-parallel-size 8 \
  --model-loader-extra-config '{"distributed": true, "concurrency": 32}'
```

주의: 스트리머는 SafeTensors 가중치가 필요하니 모델에 .bin 만 있지 않고 .safetensors 파일이 있는지 확인해야한다이유는 두 형식의 생김새가 다르기 때문이다, sglang도 같은 스트리머를 지원한다. 

```
.safetensors
  [헤더: 텐서 이름 → dtype, shape, 파일 안 바이트 위치(offset)]
  [텐서 데이터가 그냥 이어 붙어 있음]
  → 헤더만 읽으면 "어느 텐서가 몇 번째 바이트부터 몇 바이트"인지 전부 안다
  → 파일을 여러 구간으로 쪼개 동시에 읽고, 읽는 족족 GPU로 보낼 수 있다

.bin (PyTorch pickle)
  [Python 객체를 직렬화한 것]
  → torch.load로 역직렬화를 끝까지 해야 텐서가 어디 있는지 알 수 있다
  → 구간을 나눠 병렬로 읽는 게 불가능, 스트리밍의 전제가 깨진다
```

스트리머의 속도는 병렬로 읽어서 gpu로 동작하니까 나오는건데 그게 가능한 형식이 safetensors이다. pickle은 로드시 임의 코드로 실행할 수 있다는 보안 문제도 있어서 요즘은 safetensors가 표준

최신 공개 모델은 대부분 safetensors로 배포되지만 오래된 모델이나 사내에 `torch.save`로 저장한 파인튜닝 체크포인트는 .bin인 경우가 많아서 그 상태로 `--load-format-runai_stramer`를 켜면 로딩에 실패한다 배포 파이프라인에 safetensors 변환 단계를 미리 넣어두자. SGLang도 같은 스트리머를 지원하고 조건은 같다.

### 엔진 초기화를 줄이기

가중치를 다 올려도 끝이 아니다. CUDA 그래프를 떠올려보자

CUDA그래프는 모양이 고장돼야 해서 배치 크기별로 여러개를 미리 캡처하고 그게 기동시간과 gpu 메모리를 막게된다

- **torch.compile cache를 영속화**: 컴파일 결과를 볼륨에 저장해두면 두 번째 기동부터 재사용할 수 있다
- **캡처할 배치 크기 범위 제한:** `--cuda-graph-max-bs`를 실제 최대 배치에 맞춰서 쓰지도 않는 큰 배치를 캡처하느라 시간을 쓰지 않는다.
- **이미지 지연 로딩:** 컨테이너 이미지를 다 받기 전에 필요한 레이어부터 시작한다 SOCI, stargz 계열

### 아예 안내리는 Sleep Mode

콜드스타트가 병목이면 그냥 내리지 않는것도 방법인데 vLLM의 Sleep Mode는 프로세스를 죽이지 않고 gpu 메모리만 비운다

레벨 1은 모델 가중치를 cpu메모리로 내리고 kv캐시를 버리며 깨우는 시간은 작은 모델이 0.1~0.8초, 큰 모델은 3~6초수준이다 레벨2는 가중치와 kv 캐시 모두를 버리고 rope 스케일링 텐서같은 버퍼만 cpu에 남긴다

효과는 잠든 모델을 깨우는것이 새 vLLM 인스턴스를 띄우는것보다 18~20배 빠르다, 프로세스가 살아있으니 CUDA 컨텍스트, 컴파일 결과, 캡처한 그래프가 전부 남아있기 때문이다 콜드스타트의 4단계를 통째로 건너뛴다

```bash
export VLLM_SERVER_DEV_MODE=1
vllm serve Qwen/Qwen3-8B --enable-sleep-mode --port 8001

curl -X POST 'localhost:8001/sleep?level=1'   # 가중치 → CPU, KV 버림
curl -X POST 'localhost:8001/wake_up'         # 다시 GPU로
```

- **GPU 한 장에 모델 여러개를 번갈아 돌릴때** 트래픽이 적은 모델 여러개를 하나의 gpu에서 시분할할때 좋다
- **RL 학습:** 롤아웃(추론)과 같은 학습을 같은 gpu에서 번갈아 할때 추론 엔진을 재우고 학습에 메모리를 넘긴다

`/sleep`, `/wake_up` 같은 엔드포인트는 `VLLM_SERVER_DEV_MODE=1`이 필요하고 신뢰할 수 있는 네트워크에서만 노출해야한다. 외부에 열면 누구든 서버를 재울 수 있다.

### scale to zero는 싸지 않다
 
| 전략 | 유휴 비용 | 첫 요청 지연 | 적합한 곳 |
|------|----------|------------|----------|
| 최소 레플리카 상시 유지 | GPU 상시 과금 | 없음 | 대화형, SLO 엄격 (사례 A) |
| Sleep (레벨 1) | GPU는 점유, CPU RAM에 가중치 | 초 단위 | 모델 여러 개 시분할 |
| scale to zero + 빠른 로더 | 0 | 분 단위 | 내부 도구, 배치, 저빈도 모델 |
| scale to zero + 기본 로더 | 0 | 수 분 ~ 10분 | 사실상 대화형 불가 |

> 판단 기준: 유휴 시간 x gpu 시간당 비용 vs 콜드스타트중잃는 요청과 사용자 이탈 비용. 대화 서비스에서 첫 사용자가 5분을 기다리는건 대개 gpu 몇 시간 값보다 비쌀 수 있다.

## 멀티 LoRA 서빙 - 모델 300개를 gpu 몇장에

고객사 300곳이 각자 자기 데이터로 파인튜닝한 모델을 원한다고 해보자

풀 파인튜닝이면 고객마다 가중치 한벌이기에 8B만 해도 16GB x 300 = 4.8 TB 정도가 필요하고 70B라면 42TB, 고객마다 gpu를 따로 잡을수도 없고 대부분 고객은 트래픽이 띄엄띄엄이라 gpu가 거의 놀게된다.

LoRA로 학습하면 상황이 바뀌는데, 가중치 W는 그대로 두고 작은 행렬 두개 B, A만 학습한다

```
W' = W + B·A
W: d_out × d_in       (고정, 모두가 공유)
A: r × d_in           (고객별)
B: d_out × r          (고객별)
r: rank, 보통 8~64    (d보다 훨씬 작음)
```

### Adapter 크기 - 직접 계산해보자

Llama-3.1-8B (hidden 4096, intermediate 14336, KV 차원 1024, 32층)에 7개 모듈 전부 LoRA를 걸었다고 하자. 행렬 하나의 lora 파라미터 수는 `r x (d_in + d_out)` 이다.

```
q_proj:    4096 → 4096    r × 8,192
k_proj:    4096 → 1024    r × 5,120
v_proj:    4096 → 1024    r × 5,120
o_proj:    4096 → 4096    r × 8,192
gate_proj: 4096 → 14336   r × 18,432
up_proj:   4096 → 14336   r × 18,432
down_proj: 14336 → 4096   r × 18,432
-----------------------------------
층당 합계                  r × 81,920
× 32층                    r × 2,621,440

r = 16 → 약 4,200만 파라미터 × 2바이트 ≈ 84MB
r = 64 → 약 1억 6,800만 파라미터 × 2바이트 ≈ 335MB
```

r = 16 어댑터는 베이스 모델 16gb의 약 0.5%로 300개를 다 모아도 25GB라서 cpu ram에 넉넉하게 들어간다

#### 그냥 merge하면 안되는 이유

LoRA에 W를 더해서 W'를 만들어주면 추론 비용이 베이스와 똑같아지는데 그런데 그러면 고객마다 다른모델이 되어서 다른 고객 요청과 같은 배치에 넣을 수 없다. 배칭 이득이 전부 사라지는 것이다

병합하지 않고 그냥 계산하면 된다 이런식으로

```
y = x·W + (x·A)·B
    ─────   ─────────
    공통     고객별

배치 안의 요청 64개가 각자 다른 고객이어도
  x·W 부분은 64개를 한 번에 행렬곱 (가중치를 한 번 읽어 64개에 씀)
  (x·A)·B 부분만 요청마다 다른 A, B를 써야 함
```

문제는 두번째항으로 요청마다 다른 작은 행렬곱 64개를 따로 커널로 돌리면 커널 런치 오버헤드가 터진다.

#### 커널 런치 오버헤드

gpu에서 도는 함수 하나를 커널이라고 부른다.

행렬곱 하나도 커널 하나고 커널을 돌리려면 cpu가 매번 gpu에 '이 함수를 이 데이터로 실행하라' 라고 명령을 보내야하는데 이명령을 준비하고 보내고 gpu가 받아서 시작하기까지 **실제 계산과 상관 없이 고정으로 드는 시간이 있다** 대략 커널 하나당 수 µs 수준이다. (드라이버, 프레임워크에 따라 다름)

큰 행렬곱이면 계산 자체가 수백 µs~ms라서 이 몇 µs는 티도 안 난다. 그런데 LoRA의 x·A는 극도로 작다 즉 왓다갓다 너무 많이함

```
x·A  =  (1 × 4096) × (4096 × 16)
     → 계산량이 너무 작아서 GPU는 1~2µs면 끝냄
     → 그런데 런치에 드는 시간도 수 µs
     → 일하는 시간보다 "일 시작하라고 부르는 시간"이 더 길다
```

> 택배 기사가 물건 하나 배달할 때마다 물류센터로 돌아가서 다음 송장을 받아오는건데 배달 자체는 10초인데 왕복 5분이면 하루종일 왕복만 하니까 손해. 한번에 한 트럭에 여러번 실어보내면 좋은원리

이게 쌓이면 얼마나 되나 대략 계산해보면

```
요청 64개 × LoRA 행렬곱 2개(A, B) × 모듈 7개 × 32층
  = 디코드 한 스텝에 커널 약 28,000번
커널당 런치 비용 약 5µs로 잡으면
  = 28,000 × 5µs ≈ 140ms

디코드 한 스텝은 보통 수십 ms 안에 끝나야 한다
→ LoRA 런치 비용만으로 스텝이 몇 배 느려진다
```

> 배치를 제대로 활용하지 못해서 생기는문제

그래서 요청마다 따로 돌리는건 답이 아니며 여러 요청의 LoRA 계산을 하나로 묶는 방법이 필요하다.

### SGMV - 이질적인 어댑터를 한 커널로

Punica가 이 문제를 풀었다. 어댑터 id로 요청을 묶어서 그룹마다 배치 GEMM를 실행하는 CUDA 커널 SGMD(Segmented Gather Matrix-Vector Multiplication)를 도입했다

```
배치 내 요청: [고객A, 고객A, 고객C, 고객B, 고객B, 고객B, 고객A]
                      ↓ 어댑터별로 정렬 (segment)
              [A A A | B B B | C]
                      ↓ 한 커널 안에서 segment마다 해당 어댑터의 A, B를 gather해서 곱
              커널 런치 1번
```

이질성 비용이 생각보다 작은데 배치 64에서 어댑터가 전부 다를때는 SGMV는 116µs, 전부 같을 때는 37µs로 약 3배 차이지만 베이스 모델의 어텐션 계산에 묻힌다.

Punica는 기존 멀티 LoRA 대비 처리량 12배를 달성했고 베이스만 돌리는 vLLM과 8~12퍼센트 차이 이내 (Llama-7B, A100에서 초당 1,044 vs 1,140)였다.

S-LoRA는 메모리 관리를 더했다. 모든 어댑터를 메인 메모리에 두고 현재 실행중인 요청이 쓰는 어댑터만 gpu로 가져온다.

그리고 PagedAttention 아이디어를 어댑터로 확장해서 KV cache와 어댑터 가중치가 **같은 페이지 풀**을 공유하게 했다 (Unified Paging). 결과는 단일 A100 80GB에서 어댑터 2,000개를 동시에 서빙했고 단순 패킹 방식의 vLLM은 어댑터 5개를 넘으면 OOM이 났다.

이 두 연구가 지금 엔진들의 멀티 LoRA 구현의뿌리다. SGLang은 S-LoRA와 Puncia의 기법을 가져와 한 배치 안의 시퀀스마다 다른 LoRA 어댑터를 효율적으로 지원한다.

### 엔진 설정

**vLLM:** gpu 슬롯과 cpu 캐시 2계층

```bash
VLLM_ALLOW_RUNTIME_LORA_UPDATING=True \
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --enable-lora \
  --max-loras 16 \          # GPU에 동시에 올라가는 어댑터 수 (= 한 배치에 섞일 수 있는 수)
  --max-lora-rank 16 \      # 이 값으로 슬롯을 미리 할당한다 (아래 함정 참고)
  --max-cpu-loras 128       # CPU LRU 캐시

# 런타임에 어댑터 추가 (재시작 없이)
curl -X POST localhost:8000/v1/load_lora_adapter \
  -H "Content-Type: application/json" \
  -d '{"lora_name": "tenant-042", "lora_path": "/adapters/tenant-042"}'
```

```bash
python -m sglang.launch_server \
  --model-path meta-llama/Llama-3.1-8B-Instruct \
  --enable-lora \
  --lora-backend csgmv \
  --max-loras-per-batch 16 \
  --max-lora-rank 16 \
  --lora-target-modules all \
  --max-loaded-loras 64
```

- `max_loras_per_batch`는 배치당 최대 어댑터 수로 멀티 LoRA용 GPU 메모리 예약량에 영향을 주므로 메모리가 부족하면 작게 잡아야하며 기본값은 8이다.
- 백엔드: `csgmv`는 고동시성에 최적화된 Chunked SGMV 백엔드고 벤치마크에서 기본 triton 백엔드 대비 20~80% 지연 개선을 보였다.
- 동적 로딩: `/load_lora_adapter`와 `/unload_lora_adapter` api로 런타임에 어댑터를 올리고 내릴 수 있으며, 이때는 `--max-lora-rank`와 `--lora-target-modules`를 기동시 명시하는 것이 권장된다.
- 고정 pinning: 자주 쓰는 어댑터는 gpu에 고정할 수 있지만 너무 많이 고정하면 고정 안 된 요청이 멈출수있어 고정 개수를 max-loras-per-batch - 1로 제한한다.

### 주의점

#### 1. max-lora-rank는 최대치로 미리 할당 됨

슬롯은 어댑터 크기마다 맞추는게 아니라 `--max-lora-rank` 기준으로 잡히는데 300개중 하나만 r=64 이고 나머지가 r=16이여도 모든슬롯이 r=64로 잡힐 수 있다

```
max-loras 8 × r=16 슬롯 ≈ 8 × 84MB  ≈ 0.7GB
max-loras 8 × r=64 슬롯 ≈ 8 × 335MB ≈ 2.7GB
차이 2GB ÷ 128KiB/토큰 ≈ KV 캐시 1만 5천 토큰을 잃는다
```

고객 하나 값이 크면 다른 동시 사용자수도 깎아먹는지라 어댑터 rank 정책을 학습 단계에서 표준화하는게 서빙쪽에 최적이다 모델 설계와 서빙 설계가 하나의 결정이라는 점이 LoRA에서도 반복된다

#### 2. 접두사 캐시가 어댑터별로 쪼개진다

이건 놓치기 쉬운데 같은 시스템 프롬프트라고 해도 어댑터가 다르면 kv가 다르다.

k_proj, v_proj에 LoRA가 걸려있으면 당연하고 q/o에만 걸려있어도 앞 층의 출력(은닉상태)는 바뀌니까 뒤 층의 kv가 달라진다

```
고객 300곳 × 같은 3K 시스템 프롬프트
  베이스 모델이면: 3K 토큰 KV 1벌 → 모두가 공유
  LoRA 300개면:   3K 토큰 KV 300벌 → 캐시 키에 어댑터 ID가 들어가야 함
```

#### 3. 어댑터 친화 라우팅이 필요하다

캐시 인지 라우팅과 같은 논리로 어댑터 300개를 레플리카 4개에 무작위로 두면 모든 래플리카가 300개에 다 로드해야하고 어댑터별 접두사캐시도 4벌씩 생긴다 같은 어댑터는 또는 소수의 레플리카로 보내야 어댑토 로딩도 캐시도 산다

#### 4. 어댑터 스왑이 TTFT p99를 튀게함

gpu 슬롯에 없는 어댑터 요청이 오면 cpu또는 디스크나 원격저장소에서 가져와야해서 피크가 튀게된다

#### 5. 슬롯이 적으면 배치가 쪼그라든다

대기큐에 20개 고객 요청이 섞여있는데 슬롯이 8개면 스케줄러는 그 8개 어댑터의 요청만 한 배치에 넣을 수 있다. 나머지는 기다린다. 메모리가 남아도 배치는 커지지 않는다. 비동기 로딩 SGLang의 `--enable-lora-overlap-loading`이 이걸 완화하지만 어댑터가 각자 다른 시점에 gpu에 올라오기 때문에 여러 어댑터를 묶는 프리필 배치를 만들 기회가 줄어든다는 대가가 있다.
