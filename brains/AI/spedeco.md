# Speculative Decoding

LLM은 토큰을 하나 만들때 모델 가중치 전체를 메모리에서 읽어와야한다.

이때 gpu의 계산능력 대부분은 놀고있게 된다

speculative decoding은 이 남는 계산 능력을 이용하는 방법이다.

**작고 ㅃ른 추측 담당이 다음 토큰 여러개를 미리 써두면 큰 모델이 그걸 한 번에 채점해 맞는데까지만 받아들인다**

큰 모델을 한 번 돌릴때 토큰을 여러개 얻을 수 있으니 빨라지고, 채점 규칙을 잘 설계하면 결과 분포가 큰 모델 혼자 생성한 것과 수학적으로 똑같다.


| 용어 | 뜻 |
|---|---|
| target 모델 | 원래 쓰려던 큰 모델. "채점 담당" |
| draft (drafter) | 다음 토큰을 미리 추측하는 쪽. 작은 모델일 수도, target에 붙은 작은 헤드일 수도 있음 |
| k (num_speculative_tokens) | 한 번에 추측하는 토큰 개수 |
| 수락 / 거절 (accept / reject) | target이 draft 토큰을 받아들이는지 |
| 수락률 (acceptance rate) | draft 토큰 하나가 수락될 확률 |
| 평균 수락 길이 (MAL, mean accepted length) | 한 번 검증할 때 평균 몇 토큰을 얻는지 |
| lossless | 결과 분포가 target 단독과 완전히 같다는 뜻 |

<br>

## 왜 디코드는 느린가

> 디코드는 계산이 아니라 메모리 읽기에 묶여 있어 gpu 계산 능력 대부분이 논다.

#### 비유: 백과사전 한 질을 매번 다 넘기는 사람

어떤 사람이 글을 쓰는데 한글자를 쓸때마다 백과사전 전체를 처음부터 끝까지 넘겨 본다고 생각해보자

실제로 글자를 쓰는 시간은 1초인데 사전을 넘기는데10분이 걸리게 된다 이 사람의 속도를 결정하는건 글쓰는 속도가 아니라 사전을 넘기는 속도인 것이다 

그런데 한 번 사전을 넘기는 동안 **글자 5개를 동시에 확인할 수 있다면 어떨까** 넘기는 시간은 그대로인데 5배 많은일을 하게된다. speculative decoding이 노리는것이 이 지점이다.

70B 모델을 bf16으로 H100 한 장에서 돌린다고 가정해보자 (실제로는 한 장에 안들어가지만 계산 감을 잡기위해)

```
가중치 크기     : 70B × 2 byte = 140 GB
HBM 대역폭      : 약 3.35 TB/s
→ 가중치 한 번 읽기 : 140 / 3,350 ≈ 0.042초 = 약 42 ms

토큰 하나 계산량 : 약 2 × 70B = 140 GFLOPs
bf16 연산 성능   : 약 989 TFLOPS
→ 계산 시간      : 140 / 989,000 ≈ 0.00014초 = 약 0.14 ms
```

**메모리 읽기 42ms, 계산 0.14ms**로 배치가 1이면 gpu 계산장치는 약 99% 이상의 시간을 가중치가 도착하기를 기다리며 보낸다

이런 상태를 memory-bound라고 부른다

### 그래서 생기는 기회

가중치를 한 번 읽어 온 김에 토큰 1개가 아니라 5개를 계산해도 **시간은 거의 늘지 않는다.** 계산 장치가 원래 놀고 있었으니까. 문제는 다음 5개 토큰이 뭔지 모르는데 어떻게 5개를 한 번에 계산하느냐 이다. 다음 토큰은 이전 토큰이 정해져야 알 수 있기 때문이다.

그래서 일단 추측해두고 한 번에 확인하는 방식으로 쓴다

<br>

## 기본 동작 원리

> draft가 k개를 추측 -> target이 k개를 한 번에 채점 -> 처음 틀린 곳 직전까지 수락 + target이 그 자리에 자기 토큰 하나를 추가

### 한 라운드 따라가기

프롬프트가 `"The weather today is"` 이고 k = 4라고 해보자

```
① draft가 4개 추측:      sunny  and  warm  outside

② target이 한 번에 채점:  이 4개를 입력으로 넣고 forward 1번.
                          각 위치에서 "target이라면 여기서 뭘 골랐을까"를 동시에 계산

③ 왼쪽부터 비교:
   sunny   → target도 sunny  ✓ 수락
   and     → target도 and    ✓ 수락
   warm    → target은 clear  ✗ 거절 → 여기서 멈춤
   outside → (앞에서 틀렸으니 볼 필요 없음, 버림)

④ 결과: "sunny and" 수락 + target이 고른 "clear" 추가
        → 이번 라운드에 토큰 3개 확정

⑤ 다음 라운드는 "The weather today is sunny and clear"에서 시작
```

target을 한 번 돌렸는데도 토큰 3개를 얻었다 그냥 생성했으면 3번 돌릴거였는데

### 왜 target이 한 번에 채점할 수 있나

추측한 토큰들이 이미 정해져있기 때문이다 sunny and warm outside를 통째로 넣으면 프롬프트를 처리할때 prefill처럼 모든 위치를 병렬로 계산이 가능하다

각 위치에서 target이 내놓은 다음 토큰 예측을 보면  앞이 sunny엿다면 target은 다음에 and를 골랐을까를 한꺼번에 확인할 수 있다

### 손해 보는 경우가 없나

- **전부 틀려도** target이 첫 자리에 자기 토큰을 하나 넣으므로 최소 1개는 얻는다 그냥 생성할때와 같다
- **전부 맞으면** k + 보너스 1개 (마지막 위치 다음 토큰도 타겟이 이미 계산해둠) = k + 1개를 얻는다

그래서 한 라운드에 얻는 토큰은 1개 ~ k + 1개이고 손해는 드래프트를 돌리는 시간과 버려진 토큰을 계산한 비용 뿐이다 이 비용이 커지는 상황은 밑에서 알아보겠다.

## 결과가 원래 모델과 똑같은 경우

> greedy면 같으면 수락, sampling이면 확률 비율로 수락, 거절하면 보정된 분포에서 다시뽑기. 이 규칙 덕분에 출력 분포가 target과 정확히 같다.

### greedy (temperature = 0)

target이 항상 확률 높은 토큰을 고르는 설정이면 간단한데 **draft 토큰이 target의 1등 토큰과 같으면 수락 다르면 거절하고 target의 1등 토큰을 쓴다**

어떤 경우든 최종 토큰은 target의 1등 토큰이므로 결과가 한 글자도 다르지 않다.

### sampling (temperature > 0)

확률적으로 뽑는 경우에는 같음녀 수락 규칙을 쓰면 안된다. draft가 자주뽑는 토큰이 지나치게 많이 나오게 되기 때문이다 그래서 이런 규칙을 쓴다.

```
draft가 토큰 x를 뽑았을 때

p(x) = target이 x에 준 확률
q(x) = draft가 x에 준 확률

1) 확률 min(1, p(x) / q(x)) 로 수락
2) 거절되면, max(0, p - q)를 합이 1이 되게 정규화한 분포에서 다시 뽑기
```

1. draft가 target보다 덜 자신있게 고른 토큰 q <= p 는 무조건 수락한다
2. draft가 target보다 과하게 자신있게 고른 토큰 q > p는 과한만큼 깎아서 수락한다
3. 거절됐을때는 draft가 덜 뽑아준 몫 p - q가 양수인 토큰들 에서 다시 뽑아 부족분을 ㅐㅊ운다

### 숫자로 확인

토큰이 A, B, C 세개 뿐이라고 해보자.

```
target p = [0.4, 0.4, 0.2]
draft  q = [0.6, 0.3, 0.1]
```

draft가 A를 과하게 좋아하고 B와 C는 덜 좋아한다.

#### 수락 확률

```
A: min(1, 0.4 / 0.6) = 0.667   (과하니까 깎음)
B: min(1, 0.4 / 0.3) = 1       (무조건 수락)
C: min(1, 0.2 / 0.1) = 1       (무조건 수락)
```

**거절될 확률** (A를 뽑고 거절되는 경우 뿐)

```
0.6 × (1 - 0.667) = 0.6 × 0.333 = 0.2
```

거절 후 다시 뽑는 분포

```
max(0, p - q) = [max(0, -0.2), max(0, 0.1), max(0, 0.1)] = [0, 0.1, 0.1]
정규화        = [0, 0.5, 0.5]
```

최종적으로 각 토큰이 나올 확률은

```
A: draft가 A 뽑고 수락               = 0.6 × 0.667        = 0.4
B: draft가 B 뽑고 수락 + 거절 후 B    = 0.3 × 1 + 0.2 × 0.5 = 0.4
C: draft가 C 뽑고 수락 + 거절 후 C    = 0.1 × 1 + 0.2 × 0.5 = 0.2

최종 = [0.4, 0.4, 0.2]  =  target p 와 정확히 같음 ✓
```

draft가 아무리 엉터리여도 최종 분포는 target과 같다. draft의 품질은 **결과가 맞는가가 아니라 얼마나 빨라지는가**에만 영향을 준다

이게 speculative decoding이 lossless라고 불리는 이유다 

### 주의점: 엔진 설정에 따라 lossless가 아닐수도

서빙 엔진 중에서는 속도를 위해 수락 기준을 느슨하게 하는 옵션을 제공하는곳이 있다

예를들어서 vLLM에서는 `rejection_sample_method` 옵션이 있고 기본값은 `strict` 이다. 

기본값이 아닌 설정을 쓰려면 결과 target이 단독과 달라질 수 있으니 정확도가 중요한 평가에서는 설정을 확인하자.

## 얼마나 빨라지는지 계산해보기

> 속도 향상 = 라운드당 얻는 토큰수 / 라운드당 드는 시간, 수락률이 높고 draft가 쌀수록 좋고, k는 무조건 크다고 좋은게 아니다

### 라운드당 얻는 토큰 수 

토큰마다 수락확률이 a로 같다고 단순화 해보면 k개를 추측했을때 한라운드에 평균적으로 얻는 토큰수는 아래와 같다

```
평균 토큰 수 = (1 - a^(k+1)) / (1 - a)
```

`a^(k+1)`은 a를 k+1 번 곱한것으로 아래 표를 참고해보면 된다

| 수락률 a | k=1 | k=2 | k=4 | k=8 |
|---|---|---|---|---|
| 0.6 | 1.60 | 1.96 | 2.31 | 2.47 |
| 0.8 | 1.80 | 2.44 | 3.36 | 4.33 |
| 0.9 | 1.90 | 2.71 | 4.10 | 6.13 |

읽는법은 수락률 a가 0.8이라면 k=4일때 평균 3.36토큰을 얻게 된다는 뜻이다

k를 늘려도 효과가 점점줄어드는 이유는 앞에서 한 번 틀리면 뒤는 다 버려지기 때문이다. 수락률이 0.8이면 5번째 토큰까지 살아남을 확률은 0.8을 5번 곱한 0.33 정도기 때문이다.

### 라운드당 드는 시간

```
라운드 시간 ≈ target 1번 + draft k번
```

draft 한 번의 비용을 target 한 번의 c배라고 하면 라운드 시간은 `1 + k x c` 이다. 배치가 작아서 target이 k+1개를 검증하는 비용이 1개 생성과 거의 같다고 가정한다

### 속도 향상

```
속도 향상 ≈ 평균 토큰 수 / (1 + k × c)
```

| 조건 | k=1 | k=2 | k=4 | k=8 |
|---|---|---|---|---|
| a=0.8, c=0.05 (draft 아주 쌈) | 1.71× | 2.22× | 2.80× | 3.09× |
| a=0.8, c=0.2 (draft 좀 비쌈) | 1.50× | 1.74× | 1.87× | 1.66× |
| a=0.6, c=0.2 | 1.33× | 1.40× | 1.28× | 0.95× |
 
이 결과를 보고 알 수 있는것은

- draft가 싸면 k를 크게 잡아도 된다
- draft가 비싸면 k를 키우다가 어느순간 오히려 느려지게 된다. 가장 아래줄의 k = 8은 1보다 작아서 안쓰느니만 못하다
- 그래서 draft를 최대한 싸게 만들어 수락률을 높게 만드는게 이 분야 연구의 전부라고 해도 된다 아래에서 그 시도들을 볼것이다
- 최적의 k모델은 작업마다 다르다 실제 측정에서도 k를 키운다고 항상 좋아지지는 않았고 최적값이 모델과 워크로드에 따라 달랐다

### 수락률은 작업마다 다름

같은 draft라고 하더라도 작업에 따라 수락률이 크게 달라진다

- **잘 맞는 작업:** 코드, 수학 풀이, 정해진 형식 (JSON), 입력을 많이 베끼는 요약/편집. 다음 토큰이 뻔한 경우가 많다.
- **잘 안 맞는 작업:** 창작이나 시, 자유대화 같은것들은 다음 토큰 선택지가 넓으니 별로다
- **temperature가 높을수록** 수락률이 떨어진다 target자체가 무작위로 뽑으니 맞히기 어렵다.

DSpark를 SGLang에 붙인 실험에서는 검증 길이를 난이도에 맞춰 자동으로 조절하게 했는데 GSM8K(수학)에서는 평균 약 5.24토큰, arena-hard(일반대화)에서는 약 3.78토큰, 시 쓰기에는 약 2.91토큰을 검증했다. 작업별로 차이가 이정도로 난다.

## draft를 만드는 방법들

> 별도의 작은 모델 -> 모델 없이 문자열 매칭 -> target에 작은 헤드 붙이기(EAGLE, MTP) -> 여러 토큰 한번에 추측 DFlash, DSpark 순으로 발전함.

| 방법 | draft 정체 | 추가 학습 | 특징 |
|---|---|---|---|
| 별도 draft 모델 | 같은 계열의 작은 모델 (예: 70B에 1B) | 보통 불필요 | 가장 단순. 같은 tokenizer여야 함. draft가 상대적으로 비쌈 |
| n-gram / prompt lookup | 모델 없음. 입력에서 같은 문자열 찾아 이어 붙이기 | 불필요 | 거의 공짜. 입력 베끼는 작업에서만 효과 |
| suffix decoding | 모델 없음. 이전 출력들의 패턴 트리 | 불필요 | 반복적인 에이전트 작업에 강함 |
| Medusa | target 위에 헤드 여러 개 (각각 +1, +2, +3번째 토큰 예측) | 헤드만 학습 | EAGLE 이전 세대 |
| EAGLE 계열 (EAGLE-3) | target의 hidden state를 받는 작은 레이어 | draft만 학습 | 범용으로 가장 많이 쓰임 |
| MTP | 사전학습 때부터 모델에 들어 있는 예측 모듈 | 이미 들어 있음 | 모델이 지원하면 가장 쉬운 선택 |
| DFlash / DSpark | 블록 단위로 여러 토큰을 한 번에 추측하는 draft | draft 학습 | 2026년 최신. draft 비용을 크게 줄임 |

### 별도의 draft 모델

가장 처음 나온 방식 2023년 Google DeepMind 논문이다. 같은 tokenizer를 쓰는 작은 모델을 draft로 쓴다

- **장점:** 이미 있는 작은 모델을 쓴다
- **단점:** draft도 독립된 모델이라 kv cache, memory를 따로 쓴다. 그리고 작은 모델은 큰 모델의 생각을 모르고 혼자 추측하니 수락률에 한계가 있다.

### 모델 없는 방법 n-gram, suffix decoding

**ngram(prompt lookup)**은 최근 생성한 몇 토큰과 같은 문자열을 프롬프트에서 찾아서 그 뒤에 이어지는 토큰을 그대로 추측으로 쓰는 방법이다.

```
프롬프트에 "def calculate_total(items):" 가 있고
모델이 방금 "def calculate_" 까지 썼다면
→ 프롬프트에서 찾아 "total(items):" 를 추측으로 제출
```

코드 수정, 문서 편집, RAG 답변처럼 **입력을 많이 베끼는 작업**에서는 효과가 크다 draft 비용은 거의 0이라 트래픽이 많을때도 부담이 적다.

suffix decoding 방식은 Suffix Tree 접미사 트리라는것을 구축해 과거의 출력 이력까지 고속으로 검색하고 매칭길이에 따라 추측 길이를 유동적으로 조절한다. 

vLLM 문서도 n-gram, suffix decoding 속도 향상은 작지만 피크 트래픽에서 부담을 늘리지 않는 방법으로 분류한다.

### EAGLE 계열

draft가 혼자 추측하지 않고 target이 이미 계산한 내부 정보 hidden state를 보고 추측하게 하자라는 아이디어다.

target은 토큰을 만들 때 마지막 레이어에 다음에 뭐가 올지에 대한 풍부한 정보를 담은 벡터를 만든다.

EAGLE은 이 벡터를 받아서 작은 레이어 하나로 다음 토큰을 예측한다. target의 생각을 넘겨받으니 작은 draft로도 수락률이 높다

### EAGLE-3 (NeurIPS 2025)에서 바뀐 것

- 이전 EAGLE은 "다음 hidden state를 예측" 하도록 학습했는데 이게 제약이 되어 학습 데이터를 늘려도 성능이 잘 오르지 않았다. EAGLE-3는 이 제약을 버리고 **토큰을 직접 예측**한다.
- 마지막 레이어만 쓰지않고 **초반 중간 후반 레이어의 hidden state를 섞어서 쓴다**
- **training-time test:** 실제 추론할때처럼 드래프트가 자기 출력을 다시 입력으로 쓰는 상황을 학습중에 미리 겪게하여 학습과 추론 조건을 맞추는기법이다.

논문 기준으로 최대 6.5배 EAGLE-2보다 약 1.4배 빨랐고 sglang에서 배치 64일때 처리량이 1.38배 올랐다.

### MTP (Multi-Token Prediction)

draft를 나중에 붙이지 말고 모델을 처음 학습할때부터 다음다음 토큰도 같이 예측하게 만들어두자는 아이디어

DeepSeek V3에서 널리 알려졌고 지금은 DeepSeek V4, Qwen3-Next, Qwen3.5 계열등 많은 최신 모델이 MTP 모듈을 기본으로 갖고 나온다

사전학습 단계에서는 학습 신호를 늘려주는 역할을 하고 추론 단계에서는 그대로 draft를 슨다.

동작방식은 EAGLE과 비슷한데 target의 hidden state와 현재 토큰 임베딩을 합쳐 다음 draft 토큰을 예측하고 그 출력을 다시 넣어 다음 토큰을 예측하는 식으로 순차적 추측한다.

**별도 체크포인트가 필요 없다는게 가장 큰 장점이다.** 모델이 MTP를 지원하면 먼저 시도할 선택지중 하나

### 블록 단위 병렬 추측: DFlash, DSpark

EAGLE, MTP는 draft도 한 토큰씩 순서대로 추측한다 k=7이면 draft를 7번 돌려야하니 위에서 언급한 c x k가 커진다.

그래서 draft도 한번에 여러개 추측하면 안되나 라는 방향이 나왔다.

**DFlash(UC San Diego z-lab)**: 블록 하나를 **한 번의 forward로 추측한다** 첫자리에는 확정된 토큰을 주고 나머지 자리는 빈칸으로 둔 다음, target의 hidden state를 참고해서 빈칸을 전부 동시에 채운다. draft 비용이 k와 거의 무관해진다.

대신 약점이 있다 빈칸을 동시에 채우니 **뒤 토큰이 앞 토큰을 보지 못한다.** 그래서 앞뒤가 어긋난 조합이 나올 수 있다.

예를들어 앞자리는 of course쪽으로 뒷자리는 no problem쪽으로 예측해서 of problem같은 말이 된다.

**DSpark(DeepSeek, 2026. 6월 공개 MIT 라이센스)**는 이걸 두 가지로 보완했다

1. **semi-autoregressive:** DFlash 방식으로 블록 전체를 한 번에 대략 예측후에 아주가벼운 헤드가 왼쪽붙어 훑으면서 앞에서 이걸 골랐으니 여기는 이게 더 자연스럽다 라고 보정하는 방식이다 비싼 부분은 병렬로, 앞뒤 맞추기는 싸게 순차로 한다
2. **confidence-scheduled verfication:** draft가 토큰마다 "이게 수락될 것 같은 확률"을 내놓는다 엔진은 이 값을 보고 **요청마다 검증할 토큰 수를 다르게 정한다** 쉬운 요청은 길게, 어려운 요청은 짧게 검증해서 버려질 계산을 줄인다.

DeepSeek V4용 DSpark 체크포인트는 공개되어있고 vLLM, SGLang 모두 지원한다 2026년 7월 공개된 Kimi K3 day-0 vLLM 레시피에도 DSpark는 포함되어있다.

### 트리 검증 treee verfication

draft가 한줄만 추측하지 않고 **갈림길 마다 후보를 여러개 두어 나무 모양으로 추측하는 방법도 있다.**

```
            ┌ sunny ── and ── warm
The weather ┤
today is    └ clear ── and ── cool
```

target은 이 나무 전체를 한 번에 검증한다. 각 토큰이 자기 조상 토큰들만 보도록 특수한 attention mask(트리마스크)를 쓴다.

한 줄이 틀려도 다른 가지가맞을 수 있어 평균 수락 길이가 늘어난다 대신 검증할 토큰 수가 늘어나므로 배치가 클땐 부담읻 ㅚㄴ다.

EAGLE-2이후 EAGLE계열이 이 방식을 채택해서 쓰고있다.

## 돌려보기

`--speculative-config`에 method와 k만 넣으면 바로 써볼수있다 중요한건 켜고나서 수락률을 확인하는것이다.

### 설정 예시

MTP 지원 모델이면

```bash
vllm serve <MTP 지원 모델> \
  --speculative-config '{"method": "mtp", "num_speculative_tokens": 3}'
```

EAGLE-3 draft를 따로 받아서 쓰는 경우:

```bash
vllm serve <target 모델> \
  --speculative-config '{"method": "eagle3", "model": "<EAGLE-3 draft 경로>", "num_speculative_tokens": 4}'
```

n-gram(모델 불필요)

```bash
vllm serve <target 모델> \
  --speculative-config '{"method": "ngram", "num_speculative_tokens": 4, "prompt_lookup_max": 4}'
```

method에 들어가는 값으로는 `draft_model`, `ngram`, `suffix`, `mtp`, `eagle3`, `dflash`, `dspark` 등이 있다. 옵션 이름과 지원 모델은 vLLM 버전마다 자주 바뀌므로 버전 문서에서 꼭 화깅ㄴ하자

### 모니터링 지표

- **수락률 / 평균 수락 길이:** vLLM은 Prometheus 지표 (`/metrics`)와 로그로 드래프트 수락 통계를 내보낸다 평균 수락길이가 1.5도 안되면 드래프트 비용만 쓰고있을 가능성이 크다.
- **TPOT / ITL(토큰 사이 지연):** speculative decoding이 줄이려는것이 이거다
- **전체 처리량:** 동시 요청이 많을때 오히려 떨어지지 않는지 확인하자

### 주의점 

- **반드시 실제 트래픽과 비슷한 프롬프트로 측정하라:** 벤치마크용은 수학문제에서도 3배 빨라지는데 실제 서비스 대화에서는 1.3배일수도
- **동시 요청 수를 바꿔가며 돌리자:** 요청 1개일때 빨라도 64개면 느려질수있다
- **temperature를 실제 서비스와 일치 시키자**

## 서빙에서의 현실: 배치가 커지면 효과가 줄어든다

> 동시요청이 많아지면 gpu가 더이상 놀지 않으므로 추측비용과 버려지는 계산이 그대로 손해가 된다

맨처음에 speculative decoding이 효과있었던 이유는 gpu 계산장치가 놀고있었기 때문이다 그런데 서빙에서는 요청 여러개를 묶어 한 번에 처리한다 (batching). 요청 64개를 묶으면 가중치를 한 번에 읽어서 64개 토큰을 계산하니 놀던계산 장치가 이미 꽤 바빠진다

```
배치 1   : 가중치 읽기 >>>>> 계산       → 계산 장치 대부분 놂 → 추측 검증이 거의 공짜
배치 64  : 가중치 읽기 ≈ 계산           → 놀 여유가 적음      → 추측 검증에 비용이 듦
배치 256 : 가중치 읽기 < 계산           → compute-bound      → 버려지는 토큰 = 순수 손해
```

### 실측 결과

- vLLM 문서는 speculative decoding을 **중간~낮은 QPS의 memory-bound 워크로드에서 토큰이 지연을 줄이는 기능**으로 소개한다 처리량을 무조건 늘려주는기능이 안디ㅏ.
- UC Berkely 팀이 MLSys 2026에서 발표한 Speculative Decoding: Performance or Illusion?는 실제 서빙 시스템과 현실적인 워크로드로 측정했다. 결론은 실제 속도 향상은 있지만 **배치가 커질수록 줄어들고, 큰 모델일수록 그렇다는 것**이다. 실행시간의 병목은 검증단계였고 수락률은 토큰 위치, 요청, 데이터셋마다 달랐다.
- Meta Llama에 EAGLE은 실서비스 규모로 최적화해서 **큰 배치에서도 1.4~2.0배를 얻었다고 보고했다** 잘최적화하면 큰 배치에서도 이득이 남는다는 사례다

### 대응 방법

- **부하에 따라 k를 조절하거나 끄기: 한가할때는 길게, 바쁠때는 짧게 예측한다**: vLLM에는 트래픽이 들쭉 날쭉한 경우를 위한 dynamic speculative decoding 옵션이 있다
- **요청마다 검증 길이를 다르게:** DSpark의 confidence scheduler가 이 방식으로 실험에서도 배치1에서는 검증 토큰수를 줄여도 이득이 작았지만 동시 요청이 늘수록 길이를 조절하는 쪽이 고정 길이보다 앞섰다.
- **draft 비용 낮추기:** n-gram처럼 거의 공짜인 방법이나 DFlash, DSpark처럼 한번에 여러개를추측하는 방법을 쓴다.

### 서빙 엔진 내부에서 생기는 문제들

#### KV Cache 롤백

target을 검증하면서 draft토큰 k개의 KV cache를 미리 만들어두는데 거절된 토큰의 kv는 버려야한다 일반 attention은 kv가 토큰 위치별로 저장되므로 이 위치 이후는 무효. 라고만 하면 된다. 

#### 고정 크기 state를 쓰는 모델 (linear attention, SSM 하이브리드)

Qwen3.5처럼 일부 레이어가 Gated DeltaNet, Mamba같은 linear attention이나 SSM인 모델은 사정이 다르다

이 레이어들은 kv cache대신 **지금까지 모든 토큰을 요약한 고정크기 state** 하나를 갱신한다.

draft토큰까지 반영해서 state를 갱신해버리면 일부만 되돌릴 방법이 업삳. 

해법은 두가지 인데

1. draft 토큰마다 중간 state 스냅샷을 저장해두고 수락된 위치의 스냅샷만 고른다 메모리와 대역폭이 많이든다
2. state를 바로 갱신하지 않고 입력만 버퍼에 쌓아뒀다가 수락된 만큼만 반영한다 NVIDIA의 ReplaySSM이 이 방식이고 120B 급 모델에서 speculative 처리량을 1.85~2.10배 올렸다고 보고했다.

MTP를 기본 탑재한 하이브리드 모델이 늘면서 2026년에 이 주제의 논문이 많이 나왔다.

### 스케줄링과 CUDA Graph

요청마다 수락되는 토큰 수가 다르므로, 다음 라운드에서 요청마다 처리할 토큰수가 들쭉날쭉 해진다

GPU 커널을 미리 녹화해두고 재생하는 CUDA graph는 입력이 고정이어야 효율적으로 맞추기가 까다롭다

SGLang의 DSpark 구현은 요청들을 빈틈없이 한 버퍼에 채우고 전체 토큰수에 맞는 graph를 골라 재생하는 방식으로 해결했다.

### 배치 내 정합성

배치 안의 요청마다 수락 길이가 다르면 kv cache 위치, 패딩 등 맞추기가 까다롭고 잘못 구현하면 **출력이 미묘하게 깨지는** 버그가 생긴다

2025 2026년 연구중 기존 배치 speculative decoding 구현들이 출력 동일성을 지키지 못한다는 걸 보인것도 있다

직접 구현하거나 엔진 수정할때는 greedy 설정에서 speculative를 켰을때와 껐을때 출력이 한 글자도 다르지 않은지부터 테스트해보자
